# 0008. セッションCookie検証失敗を try/catch で握りつぶさない(fail loud)

## ステータス

Accepted (2026-09-08)

## コンテキスト

`src/middleware/session.ts` の匿名セッション判定は、Cookieから取得した
JWTを `hono/jwt` の `verify()` で検証し、`sub`(セッションID)を取り出す。
`verify()` は検証に失敗した場合(署名不一致・期限切れ・改ざんなど)、
`null`/`undefined` を返すのではなく例外を投げる。

自動コードレビューにより、この `verify()` 呼び出しが `try`/`catch` で
保護されておらず、無効なCookieを送るリクエストがすべて500エラーになる
(ADR 0002が想定する「検証失敗時は新規匿名セッションを発行する」という
フォールバックが機能しない)という指摘があった。

過去にも一度、この箇所へ `try`/`catch` によるフォールバック処理を
追加したことがあるが、その際はプロジェクトオーナー自身の判断により
明示的に差し戻されている。この経緯から `AGENTS.md` には既に
「バグ修正は根本原因のみを最小diffで直し、頼まれていない防御的な処理を
予防的に追加しない」という規約が追加済みである。今回の自動レビューの
指摘についても、プロジェクトオーナーは同じ判断を維持することを
明示的に選択した。

## 決定

1. **`verify()` の呼び出しを `try`/`catch` で保護しない。** 検証に
   失敗した場合、リクエストはハンドラ内で例外により失敗し、500
   エラーを返す。
2. **この挙動は意図的なものであり、「バグ」ではなくプロジェクトオーナーの
   設計判断として確定する。** 自動レビュー・静的解析等が今後この箇所を
   指摘した場合も、この ADR を根拠に対応不要と判断してよい。実装を
   変更するのは、プロジェクトオーナー本人が明示的に指示した場合のみに
   限る。

## 検討した代替案

- **`try`/`catch` で検証失敗を捕捉し、新規匿名セッションへフォールバック
  する案**: 実装は容易だが、以下の理由により採用しない。
  - 検証失敗(署名不一致・期限切れ・改ざん)は通常運用ではほぼ起こらず、
    発生するとすれば `SESSION_SECRET` のローテーションミスや、Cookie
    改ざんの試行など、本来は目立つべき異常事態である。フォールバックで
    静かに新規セッションを発行してしまうと、この種の異常に気づく機会を
    失う(fail silent)。
  - 500エラーとして表面化させる(fail loud)ほうが、ログ・監視から
    異常に気づきやすい。
  - `AGENTS.md` は頼まれていない防御的な処理を追加しない方針を既に
    明文化しており、この案はそこに例外を作ることになる。

## 影響 (Consequences)

- 期限切れ(発行から1年後)・改ざん・`SESSION_SECRET`変更後に古い
  Cookieを持つリクエストは、新規匿名セッションが発行されず500エラーに
  なる。当該ブラウザはCookieが削除されるか新しいセッションが発行される
  まで影響を受け得る。
- 自動コードレビュー・静的解析ツールがこの箇所を将来指摘した場合は、
  この ADR を参照して差分適用を保留し、プロジェクトオーナーの承認を
  得てから実装を変更する。
